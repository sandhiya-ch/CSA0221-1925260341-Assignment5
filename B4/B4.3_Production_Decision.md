B4.3 – Production Decision

1. Aim

To decide the best way to store and search donor records when the blood bank connects 25 hospitals and the number of donors increases to 100 times the present number.

2. Available Strategies

Strategy 1: Keep All Donors in Memory

- Load all donor records into a growable list.
- Searching and checking eligibility can be performed directly in memory.
- Searching an unsorted list takes O(n) time.
- Memory usage is O(n).
- Suitable when the complete donor list fits comfortably in available memory.

Strategy 2: Read the File in Batches

- Load a limited number of donor records at a time.
- Process each batch and release its memory before loading the next batch.
- Memory usage is O(b), where b is the batch size.
- Processing all records takes O(n) time.
- Suitable when the donor database is too large to load completely into memory.

Strategy 3: Use a Separate Sorted Index File

- Store donor IDs and their file offsets in a separate sorted index.
- Use binary search to locate a donor.
- Searching takes O(log n) file reads.
- Memory usage can remain O(1) when the index is searched directly from the file.
- Suitable when frequent individual donor lookups are required.

3. Comparison

Strategy| Search / Processing| Memory Usage
All donors in memory| O(n) for unsorted search| O(n)
Read in batches| O(n) to process all records| O(b)
Sorted index file| O(log n) file reads per lookup| O(1) auxiliary memory

4. Production Recommendation

I recommend using a separate sorted index file for a large donor database when frequent individual donor searches are required.

For the nightly eligibility report, records can be processed in batches. This avoids loading the entire donor database into memory.

If the complete donor list is small enough to fit comfortably in memory, the growable donor list is also a simple and effective solution.

6. Conclusion

For a growing blood bank system connected to 25 hospitals, a separate sorted index is useful for individual donor searches, while batch processing is suitable for nightly eligibility reports. The final implementation should be selected based on measured execution time, memory usage and memory safety.
